## 计数规则

只有知道它到底在数什么，这些数字才有用。

| 规则 | 行为 |
| --- | --- |
| **只认成功锚点** | 用量取自 `assistant/message`（已完成的步）与 `compaction/summary`（一次压缩调用）。失败或被取消的尝试不会追加这两种事件，因此永远不计入。 |
| **流式样本是替换，不是相加** | 同一步先出 `usage` chunk、后出最终消息时，最终值**替换**早期样本——无论哪种情况都算一次调用。 |
| **`totalTokens` 是推导出来的** | 它是四个桶之和，绝不采信提供方自己的总量字段。在 15,778 份真实用量报告上两者完全一致，而推导能让桶与总量在构造上永远自洽。 |
| **推理 token 是子集** | 单独报告，绝不相加进总量，因为它本来就在 `outputTokens` 里面。 |
| **按本地日历日** | 是你所在时区的日，不是 UTC 日。 |
| **fork 切、委派子代理与 resume 不切** | 见下。 |
| **调用计到真正服务它的模型** | 路由取自会话自己的请求头，即便那个请求头落在折叠跳过的前缀里。 |
| **一个会话只由一个来源折叠，并且跟着那个来源走** | 磁盘折叠与实时折叠绝不推进同一个会话；谁接手了它，谁就一直读它。 |

### fork、委派子代理与 resume 的区别

存储的日志可能以一段"已经记录过的历史"开头。三种完全不同的情况会产生这种前缀，
把它们搞混是用量插件静默算错的最常见原因：

- **fork**（有 `parentSession`，且 `isSeeded` 为真）：前缀是**父会话**的历史，
  已经在父会话自己的日志里计过。在这里再计一次就是重复计入——必须切掉。
- **委派子代理**（有 `parentSession`，但 `isSeeded` 为假）：日志是子代理自己的，
  从第一个事件起就是；父会话只是来源信息，不是历史。切掉会连子代理自己的调用
  一起丢掉——不能切。
- **resume**（没有父会话）：前缀是**这个会话自己**更早的历史，只存了一次。
  切掉就是漏计——不能切。

`isSeeded` 正是 harness 自己对"这个会话是否含 fork 继承前缀"的回答，所以由它决定切不切。
只看 `parentSession` 会把 fork 与委派混为一谈：在一个真实 home 上，93 个委派会话全都带父会话，
把它们切掉会让重算出来的账本少掉 **892 次调用、119,393,450 token**——而这些调用全部发生在
子代理创建之后，不可能有别的会话替它们记账。

### 调用计到真正服务它的模型

一次调用的提供方与模型来自会话的 `request/header`。实时会话的第一个请求头落在实时折叠
跳过的前缀里——也就是会话被创建时的种子——所以只从后续事件里读路由，会让最早的那几次调用
被记到 `unknown/unknown`，尽管模型是已知的：同一个真实 home 上是 **72 次调用、
10,059,207 token**。现在路由会从被跳过的前缀里读出来，和磁盘折叠读它的方式一致，
于是调用会计到真正回答它的模型上。

路由也会从**续折**已经越过的那些事件里读出来。游标能跨重启活下来，而跟着它的路由不能，
否则新进程里折叠的第一笔调用就会被记到 `unknown/unknown`，尽管游标之前的事件已经写明了模型。

### 运行中的会话由它的日志折叠，并且日志会一直被跟着

一个会话由哪个来源折叠只决定一次，而这个选择正是计数精确的原因：从磁盘日志折叠的会话，
游标落在日志的**紧凑行**空间里，而实时事件列表给同一个会话编的是另一套号，所以实时折叠
拒绝推进它。于是日志成了唯一能推进它的东西——而对一个在挂载之后被 resume 的会话来说，
日志恰恰就是会长大的那个。

因此宿主机运行期间会一直跟着日志：宿主说在跑的会话每个活动窗口重读一次，账本拥有的每个
日志每分钟一次，退出时再一次。重读从游标处继续，只计新增的行，也只解码上次之后追加的字节
——一份 2.3 MB 的日志整份解码量到 130 ms，而只读它的尾部约 1 ms，所以跟住一个会话对宿主的
开销小到可以忽略。没有这一步，被 resume 的会话要等到下次启动才会计入——在一个真实 home 上是
**557 次调用、213,106,082 token**，而且这些调用用到的两个模型在那之前根本不出现在模型表里。

### 记不到模型的调用会被重新推导，而不是留着

`unknown/unknown` 是一条真实的行：token 确实存在，账单也必须提到它们。但这一行的出现意味着
折叠从未得知路由，而事件里写明的路由值得再读一遍。存储账本的游标声称该会话已被完全消费，
所以这行否则就是永久的——修正后的折叠永远不会回头看游标之前。

加载时，凡是拥有这种行的**实时折叠**会话都会被交还给折叠：它的行会从每个聚合里减掉
（它们正是用量交叉表的精确求和，没有任何近似），游标被丢弃，然后折叠会从它的日志重读它
——日志不在了就从会话存储重读。调用于是计到真正服务它们的模型上。如果连记录都不在了，
这些 token 会跟着这一行离开账本：记不到模型的行本来就无法计价，留着它只会让
"这到底是什么模型"永远无法回答。

由**磁盘折叠自己**写下的那行则不会被处理。重读那份日志会推导出同一个键——日志里任何地方
都没有写明路由——所以修它只会每次启动都整份解码一遍而永远不收敛；那一行是那份日志的事实，
不是一段需要撤销的旧归属。


## 审计能区分两类差异

运行中的宿主是按防抖写入账本的，所以活跃会话比文件"新一点"是常态。
把这种情况报成数据损坏，审计就废了。账本自己的 `updatedAt` 可以裁决：

- 有差异的会话，其最新事件**比账本更新** → 只是还在跑 → **通过**，并报出尚未落盘的量；
- 有差异的会话，其最新事件**早于账本**，或者某条日/模型行与它本该汇总的折叠结果矛盾
  → **不通过**，退出码 1。

```
  audit: match — 1 session(s) advanced after the ledger was written
         (1 calls, 5100 tokens not yet flushed)
```
